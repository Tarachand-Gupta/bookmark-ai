# Unified browser library — research proposal awaiting approval

**Status: proposal, revised October 2, 2026. No implementation or release is authorized here.** This supersedes the September 30 cross-browser replication proposal. Bookmark AI collects eligible native bookmark additions **into its library only**. This feature makes no cloud-to-native writes and never creates, moves, or deletes native bookmarks in any browser. A card is available from signed-in web/PWA, extension, mobile, and Mac clients; “Mobile” describes a save source, not a library available only on a phone.

## Product contract and everyday journey

Collection starts **off for each browser profile**. Setup identifies the signed-in account, observed profile, and selected folders, requests the browser's bookmark permission, explains that permission may expose the whole native tree, and previews the collection scope. A successful enrollment snapshot establishes a baseline: existing nodes stay outside collection unless the user selects exact occurrences in a reviewed import. New occurrences observed afterward within scope, including nodes delivered by Chrome/Firefox's own Sync from another device, can become sources. The badge says “Observed in Chrome profile A,” not “first starred on this device.” The extension cannot reliably tell a local star from a vendor Sync arrival. Bulk import/restore floods pause automatic enrollment for preview or review; event timing alone does not prove user intent. Turning collection off stops new observations and preserves native bookmarks. Settings shows profile identity, scope, permission, last successful reconciliation, pending work, and errors.

One library card can have several **source records** for the same URL: Chrome profile A node 17 in “Research,” Firefox profile B node 9, another Firefox node 14 in “Work,” an Android app share, and a manual web save. The card is deduplicated for browsing; its sources are not deduplicated. Source badges and filters show each live *observed* browser/profile and folder context where useful, plus independent app saves. They do not infer an upstream phone or Safari origin from a Chrome node synced by the browser vendor. Browser and device filters match source records rather than one overwritten `browser` column. A native removal withdraws **only the exact source occurrence**. Its badge disappears once confirmed. The card remains while any other source or independent retention exists.

If the last source disappears, hide/remove the library card unless the user explicitly saved it independently or chose **Keep in Bookmark AI**. Proposed rule: marking Favorite or assigning a Bookmark AI Folder transparently creates a **sticky Keep** choice; explain at the action (“Also keeps this card in Bookmark AI if its browser bookmark is removed”). Unfavoriting or removing a Folder membership does not undo Keep or hide the card. A separate **Remove from Bookmark AI** action clears independent retention and removes the card; if a native source remains, suppress that exact occurrence so a later scan cannot restore it. Metadata enrichment and passive viewing do not create retention. This sticky rule needs approval because an organizational action changes future removal behavior.

An Android Chrome **Share → Bookmark AI** action saves an app record. It does not create a Chrome native star or claim a native Chrome source; label it “Mobile” with optional Android/device detail. Current mobile source detection already records `browser: "other"` and mobile/tablet device metadata ([mobile API](../../apps/mobile/src/api.ts)); the new source model must preserve that distinction. An iOS Safari share to the app or Safari extension save is likewise an app/extension save, separate from a native Safari bookmark. The same library is visible on every signed-in client. Direct **Delete from Bookmark AI** removes the card from the account's library but never touches native bookmarks. Record suppression for the exact known source occurrences so a later scan cannot restore the card. Explicit resave/Keep or a genuinely new native occurrence can make it visible again; an old node merely moved, renamed, or replayed after an outage cannot.

## Platform evidence and Safari research

Chrome and Firefox desktop expose bookmark nodes/events and are candidates after implementation and real-profile QA ([Chrome API](https://developer.chrome.com/docs/extensions/reference/api/bookmarks), [Firefox API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/bookmarks)). Firefox lacks some Chrome import/reorder event hooks, so it needs snapshot and bulk-event safeguards ([compatibility data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/bookmarks.json)). Edge documents bookmark API support but needs its own build/runtime QA ([Microsoft support table](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/api-support)); Brave compatibility likewise needs a verified Bookmark AI build and real profile ([Brave guidance](https://support.brave.com/hc/en-us/articles/360017909112-How-can-I-add-extensions-to-Brave)). Do not name either as supported until those gates pass.

**Safari/iCloud research, October 2:** iCloud Drive permission does not grant access to Safari's sync data: Apple documents app-associated containers ([iCloud configuration](https://developer.apple.com/documentation/xcode/configuring-icloud-services)). Radian's developer [claims Safari iPhone synchronization](https://x.com/oleksiibe/status/2085762465938235523), with a [follow-up claiming bidirectional iCloud sync without Full Disk Access](https://x.com/oleksiibe/status/2085762469260124353). The inspected posts do not disclose its implementation; we have not reproduced it.

A read-only Mac companion is a plausible investigation: [Chromium's Safari importer](https://chromium.googlesource.com/chromium/src/+/main/chrome/utility/importer/safari_importer.mm) reads local Safari data, and Apple supports [sandboxed user-selected file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox). Current Safari protection, profile coverage, stable source identities, file replacement, and iCloud refresh must be proven. The Mac must run to collect changes. WebKit also implements a bookmarks API behind build/runtime/permission gates, with an upstream testable preference defaulting off; test the exact shipping Safari version before making an availability claim. API implementation is not proof of shipping exposure.

[Apple's documented Safari export](https://developer.apple.com/documentation/safariservices/importing-data-exported-from-safari) supports user-mediated bookmarks and Reading List import. [iCloud for Windows](https://support.apple.com/en-euro/guide/icloud-windows/icw4a50de3c3/icloud) offers an official bridge into browser bookmarks; observation by Bookmark AI is a testable inference, and cannot reliably prove a node originated in Safari. BrowserKit's mobile browser transfer is user-mediated and subject to browser eligibility, not general background iCloud access. Full findings and sources: [research note](../../.work/universal-sync/safari-icloud-research-20261002.md).

Before promising native Safari collection, approve a **2–3 engineer-day isolated read-only spike**: feature-test Safari's API, then test sandboxed local access, iPhone-to-Mac updates, profiles/Favorites/Reading List, restart/replacement, offline and revoked permissions. Use disposable accounts and synthetic data; require complete snapshots before any source removal. This is additional to the build estimate below; production and App Store suitability remain separate gates. Mobile share saves already work independently of a native-browser collector.


## Source identity, reconciliation, and migration

Model an account-scoped library card plus a many-to-one source table. A native source key includes opaque installation/profile identity, browser, and native node ID, with a source generation to distinguish removal/recreation or ID reuse. Store original and current native folder paths separately, observation revision, enrollment evidence, state, and minimal tombstone/suppression metadata. The same URL twice in one Firefox folder, in different folders, or in different Firefox profiles yields different sources. Do not treat URL, title, folder, timestamp, browser `syncing` flag, or apparent device as proof that two nodes are the same. HTTP(S) is the initial scope; unsupported schemes get a visible skip count. Preserve meaningful query strings and fragments; a proposed normalization policy needs fixtures before any merge.

Native additions use account/profile-scoped idempotency keys and acknowledged source upserts. Persist a durable pending queue with bounded size, backoff, retry visibility, and a cap on inventory/API work. Replayed events may update the *same* source but may not create duplicate source records. Do not drop failed removals or let late adds defeat a tombstone or a user's library deletion. If authorization changes, pause that profile's queue; another account cannot inherit its source ledger. Device credentials need the narrow read/write scope for their own profile. Aggregate failure counts are sufficient analytics; never send URL/title or whole-tree telemetry.

An event is a hint. Reconcile with a **complete, successful snapshot** of the enrolled profile before inferring that a missing node was removed. A partial scan, offline browser, revoked permission, API error, interrupted worker, or capped inventory is not evidence of deletion. Folder deletion may report only the parent event; reconcile its descendants before withdrawing them. A missing local ID map, reinstall, profile reset, native ID reuse, or conflicting account makes ownership ambiguous: preserve the card/source as unresolved and offer review. The enrollment baseline and observed profile/folder scope establish which occurrences are newly seen; they do not establish the originating device. Vendor Sync arrivals within scope may be collected. Large or ambiguous import/restore batches pause for preview/review without promising reliable intent classification. Moving or editing a known node updates its current location/content without creating a new source; unclear identity changes require review. Native collection never needs permission to modify the native tree.

The current implementation is **not this contract**. Its account-level additions setting defaults on, optional “full sync” removal uses `local:nativeSyncIds` keyed by URL, and removal can call library DELETE by the remembered ID ([native-sync.ts](../../apps/extension/lib/native-sync.ts), [sync-settings.tsx](../../apps/web/components/library/sync-settings.tsx)). Library insertion upserts by URL ([bookmarks.ts](../../packages/db/src/queries/bookmarks.ts), [ingest.ts](../../packages/engine/src/ingest.ts)). Thus a source removal could target an independently saved old row; this is a code-supported risk, not a reported production incident. Migration must preserve all existing rows and treat old URL-only ownership as **unknown**. Do not retrofit old source badges, infer destructive authority, or delete an old card from a legacy map. Explicit new enrollment/review may attach a verified source while retaining the independent old save. Back up and export source, folder, Favorite, Keep, and suppression state; support rollback without orphaning independent saves.

## Organization and user controls

Keep four concepts separate: native browser folders (observed original/current source paths), user-created Bookmark AI **Folders** (nested; one card may be in several), AI categories/tags, and **Favorites**. A Favorite uses a heart or pin, not a browser star. Bookmark AI Folder changes and Favorite changes never alter a native bookmark or its folder. A Folder deletion removes membership, not its cards or sticky Keep choice. Native folder paths remain source-specific and cannot implicitly create app Folders. Web/PWA, mobile, Mac, and the extension library view should show consistent source badges, filters, Favorites, and app Folders. Source retention should be understandable from the card detail and removal feedback, for example “Firefox bookmark removed; kept in Bookmark AI because you favorited it.”

## Acceptance cases and release gate

| Situation | Required library outcome | Native outcome |
|---|---|---|
| One Chrome source, no retention; its node is removed | Source withdrawn; last-source card hidden after confirmed reconciliation | No Bookmark AI native write |
| Chrome and Firefox sources for same URL; Chrome removed | Firefox source/card remain; Chrome badge disappears | Firefox node untouched |
| Two Firefox same-URL nodes in one folder, plus one in another/profile; one removed | Exactly that occurrence withdrawn; other Firefox badges/card remain | Other native nodes untouched |
| Chrome source plus manual/mobile/Safari-share save; Chrome removed | Card and independent save remain; Chrome badge disappears | No native write |
| Only source removed from Favorite or app Folder card | Card remains by sticky Keep; later unfavorite/Folder removal still preserves it until separate Remove from Bookmark AI | No native write |
| Cloud card deleted while native source remains | Card hidden; scan replay suppressed until explicit resave/new occurrence | Source node untouched |
| Baseline node not explicitly selected, ambiguous bulk import/restore, legacy URL-only row, or lost profile IDs | No silent source adoption or deletion; old row preserved, ambiguity visible | Native nodes untouched |
| New in-scope Chrome node delivered by Chrome Sync from another device | Chrome profile is an observed source; no inferred phone/original-device badge | No native write |
| Snapshot fails/permission revoked/offline | No inferred native removal; pending state visible | Native nodes untouched |

Test account switching, reinstall, ID reuse, browser Sync on/off, nested folder deletion, move/rename, identical URLs with different query/fragment, event replay, retries, worker crash, queue overflow, and large inventories (1k/10k/50k). Verify complete-snapshot semantics and suppression across disconnect/reconnect. Check actual Chrome and Firefox profiles before a supported claim; gate Edge/Brave and Safari separately. Verify web/PWA, extension, Mac, iOS, and Android viewing and organization behavior where each is claimed. Test app share flows against native-star state on physical mobile devices. Migration/export and privacy copy are release gates.

## Scope, rough timing, and marketing

Assuming one experienced engineer, reusable account auth/API, isolated test profiles, and a safe development database, a **Chrome/Firefox beta** is a rough **10–16 engineer-days**: occurrence schema and legacy migration (3–5), scoped protocol/retries/reconciliation (4–6), enrollment/card source UI and real-profile QA (3–5). **All original clients** add roughly **8–14 days**: Folders/Favorites/sticky Keep and source filters across web/PWA, extension, Mac, iOS, and Android (5–8), then export, physical-device, privacy, and release QA (3–6). The combined **18–30 engineer-days** is an untested planning estimate, not a delivery commitment; sequencing, defects, and review can extend calendar time. Safari research/qualification, Edge/Brave qualification, and store review are excluded. The beta may claim access only on clients actually verified with the source model. A browser prototype cannot establish deletion safety or migration correctness.

Keep **Live Tabs first** in landing-page hierarchy. The second story, after release gates, can say: “Save a bookmark in a connected browser and find it in your Bookmark AI library on your devices. Add your own saves, Folders, and Favorites in one place.” Name only verified collection browsers; explain that optional collection starts per profile and that deleting in Bookmark AI does not unstar a browser. Avoid “every browser,” browser-to-browser replication, “unstar everywhere,” native Safari/iCloud claims, and “mobile-only library.”

**Approval decisions:** confirm last-source removal and sticky Keep from Favorite/Folder actions, opt-in baseline/import and observed profile/folder scope, and the Chrome/Firefox beta versus all-client rollout. Resolve Safari collection after the linked research and proposed spike are reviewed. No production or app code change follows from this document alone.
