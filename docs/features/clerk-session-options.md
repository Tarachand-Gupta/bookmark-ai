# Clerk session options — research and current code audit

Reviewed 3 October 2026. Proposal only: no app code, auth settings, billing, or production accounts changed. Production plan and configured lifetime have **not** been verified. The September 16 investigation measured exactly seven days on sampled **development** sessions; this is historical evidence, not a production measurement.

## Recommendation

Updated goal: **no Pro subscription; return after two–three inactive weeks without signing in again**. A rolling seven-day window cannot meet that inactive-gap requirement. Clerk's Hobby seven-day maximum also cannot be rolled forward by ordinary SDK token refresh.

Recommend retaining Clerk for initial identity verification and creating a **server-owned opaque device session with 30-day inactivity expiry**. Store one independently revocable record per device, with a hashed secret, user ID, display name/platform, created/last-used timestamps, expiry and revocation status. Set an explicit absolute lifetime separately (for example 90 days, pending product choice). The app presents its own signed-in state and device-session controls after Clerk expires. Clerk profile/security operations can ask for fresh Clerk sign-in when needed. No paid Clerk configuration is required; existing database/hosting usage still has cost.

The proposed **30-day Clerk custom JWT plus server record** is also feasible for a narrower initial implementation. It must validate signature, issuer/audience, expiry **and** an active application record on every authenticated request. The opaque alternative is simpler once every request already needs a database lookup. Neither is a mere dashboard setting. Keep existing extension device credentials scoped until a deliberate migration; their current limitations do not mean JWTs inherently cannot be made revocable.

## Check of the supplied workaround claims

1. **Seven days:** current [pricing](https://clerk.com/pricing) explicitly lists Hobby session duration as fixed to seven days. [Session options](https://clerk.com/docs/guides/secure/session-options) says seven days is the default for new instances and custom production lifetimes require a paid plan; development can test customization. Maximum lifetime expires regardless of activity. Opening the app refreshes short-lived API tokens, not this hard deadline. At least maximum lifetime or inactivity timeout must remain enabled.
2. **Price:** Pro includes custom session lifetime. Live pricing displays **$20/month billed annually**; Clerk's [June 2026 pricing explanation](https://clerk.com/articles/clerk-pricing-explained) states **$25/month monthly**. Annual base commitment is $240; monthly is $300 over twelve months. Published included usage is 50,000 monthly retained users per app, then metered usage; actual checkout, taxes, discounts and grandfathering remain unverified.
3. **Long JWT:** the 10-year number is supported: Clerk's [Postman/Insomnia testing guide](https://clerk.com/docs/guides/development/testing/postman-or-insomnia) documents a maximum of **315,360,000 seconds**. Thirty days falls within that. Pricing includes custom JWT templates on Hobby. However, [custom JWTs](https://clerk.com/docs/guides/sessions/jwt-templates) are not inherently session-bound and omit session claims such as `sid`. They do not extend Clerk frontend sign-in or automatically become accepted by this app's Clerk session gate. Offline signature/expiry verification alone cannot enforce logout or account/session revocation; a stolen bearer can remain usable through its expiry unless our own online controls intervene. The official long-token example is for API testing, not an endorsement of ten-year production login tokens.
4. **Sign-in ticket:** [createSignInToken](https://clerk.com/docs/reference/backend/sign-in-tokens/create-sign-in-token) documents **30 days as the default**, not a verified maximum. [Backend API](https://clerk.com/docs/reference/backend-api) says tickets are single-use and redeemed through the `ticket` strategy. [Revocation](https://clerk.com/docs/reference/backend/sign-in-tokens/revoke-sign-in-token) is available. A bridge must authenticate its own durable session before issuing a very short-lived ticket; it therefore creates a second authentication system. Do not assume it repeats password/MFA verification or carries fresh factor assurance: validate MFA/session-task behavior with the installed SDK and production policy before proposing it. Revoking Clerk alone must not allow an independent refresh cookie to silently recreate access.

## What Clerk's panel actually manages

Clerk's session/device UI manages **Clerk sessions**, not a custom array of issued template JWTs. A JWT template is an issuance recipe; each generated JWT is a separate bearer with its own `jti` and expiry. Deleting/changing the recipe does not make an already issued, offline-verifiable JWT cryptographically invalid. Logout/revocation can be enforced through our online record; store the `jti` and a hash/fingerprint rather than raw bearer strings in a user metadata array. Use a dedicated table for atomic revocation, rotation and concurrent devices.

There is a separate Clerk product that matches the remembered UI: [user API keys](https://clerk.com/docs/guides/development/machine-auth/api-keys). These are long-lived **opaque** credentials, individually revocable, and appear in an **API Keys tab** of `UserProfile` when enabled. Hobby includes 1,000 creations and 100,000 verifications/month; exceeding those free limits requires Pro. They authenticate APIs, not frontend Clerk session state. They may be useful for integrations, but their verification allowance and extra Clerk network dependency make them a less predictable basis for every app request.

Current [JWT-template docs](https://clerk.com/docs/guides/sessions/jwt-templates) explicitly exclude session-linked `sid`. We can record the original Clerk session ID ourselves, but requiring that original session to remain active would reintroduce the seven-day limit. Instead distinguish **ordinary Clerk expiry** from intentional revoke, deletion or compromised-account events and define how those events invalidate app sessions.

## Rolling versus absolute expiry

A 30-day JWT issued at login expires 30 days after issuance even if used on day29. It survives a three-week absence only when sufficient lifetime remains. A true 30-day inactivity policy updates the server record on authenticated activity, with an independent absolute deadline. JWT `exp` cannot be edited: reissue before it expires. After Clerk's session expires, the browser cannot assume `getToken(template)` can issue another token; use the independently authenticated app session to renew our credentials, or a short-lived ticket bridge to establish a new Clerk session. The latter adds another lifecycle and is unnecessary if we own app UI/auth state. A seven-day inactivity policy still signs out anyone absent for two weeks.

## Options and estimated effort

Estimates are engineering judgment for one developer familiar with the code, including meaningful cross-client verification; store review and elapsed real-time aging are additional. Prices exclude infrastructure, metering and tax.

| Option | Security/control and stability | Rough effort / cost |
| --- | --- | --- |
| Configure paid Clerk (excluded by user) | Managed session lifecycle, existing SDK renewal; longer maximum enlarges stolen-device exposure. | Not the recommendation for this free-only requirement. |
| Keep seven-day reauth | Preserves current managed expiry; user friction remains. Reconnect must preserve unsaved work and distinguish network failure from revoked identity. | 1–3 days if recovery UX needs polishing; Hobby $0 within allowance. |
| Own opaque revocable sessions | Recommended free solution; server checks device/user state and rolling inactivity. Team owns lifecycle and UI. | Bounded web/PWA + API MVP: 3–7 working days; adding Expo iOS/Android: approximately 5–10 total. Full client/lifecycle/rotation migration: 3–6 weeks. Existing infrastructure usage. |
| 30-day template JWT + online record | Feasible; issued JWT is independently revocable through our record. Clerk UI still expires. Pure offline validation is insufficient. | Similar UI/gate work to opaque sessions; bounded MVP approximately 3–7 days. JWT issuance beyond day7 needs separate recovery/renewal authority. |
| Silent ticket bridge | Preserves Clerk UI after bootstrap, but adds owned refresh sessions and two overlapping revocation lifecycles. | Roughly 2–4 weeks plus security review and operations. Not recommended solely to save the Pro fee. |

**Scope caveat:** `require-user.ts:91–103` permits extension saves, `/api/me`, settings, renewal and **per-ID bookmark DELETE**. It excludes full library/search/export/chat, but an older comment saying a stolen device token cannot delete data is inaccurate. This audit did not prove downstream deletion ownership safety. Local token removal on sign-out does not revoke a copied bearer; rotating `DEVICE_TOKEN_SECRET` invalidates all such tokens rather than one device. Existing device tokens therefore cannot be described as robust rotating/revocable sessions.

## Before implementing either owned-session option

Specify device/session records; hashed opaque refresh secrets; short-lived access credentials; atomic rotation with concurrent-refresh handling and replay detection; absolute/inactivity limits; per-device and global revoke; user deletion/ban/password-reset policy; CSRF protection and HttpOnly/Secure/SameSite web cookies; secure native storage; extension threat boundaries; online revocation enforcement for API/live connections; audit logs with no credentials; staged migration/rollback.

Test expiry boundaries, idle/reopen/offline recovery, failed refresh without data loss, logout with a copied token, remote revoke, refresh replay/concurrency, deletion and disabled accounts, MFA/session tasks, account switching, signing-key changes and every client. For paid Clerk, test new and existing sessions rather than assuming the setting retroactively rewrites expiration. Production lifetime verification and a defined revocation policy are prerequisites to an implementation proposal.
