# Free authentication options before Apple listings

Research only, 4 October 2026. No application code, provider settings, accounts, billing or deployments changed. Goal: a few thousand users, no authentication subscription, and return after two–three inactive weeks without signing in. Current production plan/configuration and Apple/Google portal registrations were not inspected.

## Recommendation

**For the imminent listings, preserve Clerk identity and the existing Apple/Google flows; add a bounded application-owned 30-day inactivity session if longer retention must ship now.** This avoids migrating accounts and provider identities, although client signed-in state, server gates and logout/revocation still need changes. It is the smallest migration, not zero work. If retention can wait, complete the listings using current authentication and schedule the session change afterward.

**For a subsequent provider replacement, Better Auth is the best fit for ownership and configurable sessions; Supabase Auth is the strongest hosted free alternative.** Better Auth fits the existing TypeScript backend and has Expo support, but we operate its database/auth service. Supabase provides a managed identity service and Swift SDK; free-project suspension and paid-only session-limit controls matter. Auth0 is viable managed authentication but is **proprietary**, not an open-source replacement, and still requires substantial integration changes.

## Comparison

All allowances are current published plans, not a promise of perpetual pricing. MAU measures monthly activity rather than all registered identities; Clerk uses a different MRU metric. A few thousand users fits the headline identity allowance of the hosted options, but email/SMS, request limits, database/egress and operational costs remain separate.

Seven-day **rolling** retention cannot cover a two–three-week absence, whichever provider owns it. Refresh credentials enable an app to recover after its short-lived access token expires; being offline does not need a continuously refreshed access token. Cookies/storage can still be cleared, credentials revoked, or absolute limits reached.

## Can we reuse Apple and Google setup?

**Often the developer registrations can be reused; swapping provider keys alone cannot migrate the app.**

Apple's [Sign in with Apple grouping](https://developer.apple.com/help/account/capabilities/group-apps-for-sign-in-with-apple/) ties web Services IDs and related apps to a primary App ID. Apple documents [team-scoped identifiers](https://developer.apple.com/documentation/signinwithapple/bringing-new-apps-and-users-into-your-team) and a separate migration procedure when ownership moves teams. Keeping the same developer team, app/Services IDs and grouping is the correct continuity strategy; changing the intermediary auth provider alone should not require an Apple app transfer. **That continuity is an inference, not proof for the existing portal setup**: verify the same Apple's `sub` on native and web test logins before migrating users. Do not create fresh identifiers or regroup apps casually.

Reuse the existing bundle IDs, Apple capability and signing registration where valid. Configure the replacement with the correct Team ID, Key ID, authorized client IDs and securely held signing key/client secret, and add its domain/callback to Apple. [Supabase's Apple guide](https://supabase.com/docs/guides/auth/social-login/auth-apple) distinguishes native identity-token exchange from browser OAuth and requires six-month secret rotation for the latter. Better Auth also supports [Apple ID-token sign-in](https://better-auth.com/docs/authentication/apple). Native nonce/token validation and account-deletion/revocation behavior must be verified anew; retaining a button is insufficient.

Google's existing Cloud project, consent configuration and appropriate OAuth clients can generally remain, subject to new authorized callback URLs. Web, iOS and Android clients are different registrations: preserve bundle/package IDs and relevant Android signing fingerprints. Validate audience and nonce using the replacement. Google specifies [stable `sub` identifiers](https://developers.google.com/identity/openid-connect/openid-connect); use verified provider identity rather than email as the migration join key.

The replacement's local user ID will differ from Clerk's `user_…`. This repository routes tenant records by Clerk user ID (`apps/web/lib/server/context.ts:192`). Preserve an internal account/tenant ID and map `(provider, verified subject)` plus old/new auth IDs to it. Otherwise existing bookmarks can appear lost or duplicate accounts can be provisioned. Apple private-relay addresses and first-login-only name data make blind email linking especially unsuitable. Export/import password hashes only after verifying target algorithm compatibility; never assume passwords, MFA enrollment, existing sessions or refresh credentials transfer. Users may need one explicit reauthentication at cutover.

## Timing and listing impact

Engineering estimates for one developer familiar with this repo, including focused QA; not quotations or promises. Clerk plus owned sessions: web/API **3–7 working days**, with Expo approximately **5–10 total**; broader Mac/extension/lifecycle coverage requires separate scope. Provider migration: a web-only proof **2–4 days**; web + Expo + safe identity mapping roughly **1–2 weeks**; all listed clients plus existing-user migration/deletion/recovery QA roughly **2–4 weeks**, potentially longer for native callback/password edge cases. Better Auth additionally requires operational readiness; hosted providers reduce that part, not client conversion.

Changing native auth normally requires new builds and repeat store QA; browser listings may need new packages/evidence. Preserve reviewer-account access, registration, Apple/Google login, logout and account deletion on iPhone/iPad/Mac and Safari; validate old-account bookmark continuity and expired/offline recovery before switching production. Actual listing statuses/build compatibility remain unverified. Lowest immediate risk is to keep provider identities stable and avoid a simultaneous store launch and provider cutover.
