# Redis-backed application sessions — proposal

Reviewed 4 October 2026. Research only; no application code, credentials, infrastructure or accounts changed. Complements [Clerk session options](clerk-session-options.md). Product constraint: initial Google/Apple identity verification through free Clerk, then independently renewable app sessions that survive two–three inactive weeks. Implementation remains pending approval.

## Recommendation and database boundary

Use a dedicated Redis instance as the **authoritative online allowlist** for our app sessions, not an ordinary cache that automatically reloads missing credentials from SQL. Signed short-lived access JWTs identify the session; a rotating opaque refresh credential renews them. Redis performs revocation, expiry and current permission checks on every protected request. SQL still serves bookmarks and other application data, and may handle login provisioning and durable lifecycle/audit records. The claim is **zero SQL reads for routine session validation**, not zero database calls overall.

Reject invalid credentials before Redis when possible. A validly signed token whose session/access record is absent gets `401`; it does **not** trigger SQL lookup, rehydration, or token creation. Apply distributed IP/request limits before JWT work, then per-user/session limits after verified identity. Repeated stolen/revoked credentials get bounded Redis checks; do not create negative-cache keys for unlimited random IDs. Redis timeout/unavailability gets `503`, preserving the client's credentials and unsaved work for retry. Distinguish a missing key from connection errors; never translate both into logout.

This sacrifices automatic recovery of evicted/lost sessions. Redis availability and durability become authentication requirements. Ordinary cache-aside is an alternative only if controlled recovery verifies current durable revocation state, rate-limits/coalesces reconstruction, and fences stale writers. It would no longer guarantee zero validation SQL reads; random/malformed tokens must still never cause SQL access.

## Key and value design

Give each **login installation/session** a cryptographically random `sid`; never use `userId` alone as a session key. One browser profile's tabs share its cookie/session; another browser profile and iOS installation each receive independent sessions. A device label is descriptive, not an identity/security boundary.

Use a namespace such as `auth:v1:{uid}:…`; braces co-locate one user's keys if Redis Cluster is later chosen. `uid` and `sid` come from verified claims or a validated refresh envelope, never an arbitrary client-supplied key.

| Key | Value | Expiry |
| --- | --- | --- |
| `auth:v1:{uid}:user` | Enabled/deleted status, current authorization version and global session generation | At least the latest live session deadline; deletion/global revoke updates atomically |
| `auth:v1:{uid}:session:<sid>` | User ID, generation, scopes, creation/last-activity/absolute/idle deadlines, platform/label, refresh-secret hash and rotation counter | `min(idleDeadline, absoluteDeadline)` |
| `auth:v1:{uid}:access:<jti>` | `sid`, generation, authorization version, token fingerprint and token expiry | JWT `exp`, with only explicitly allowed verifier clock skew |
| `auth:v1:{uid}:sessions` | Sorted set: `sid` → effective session deadline | Latest member deadline; prune expired members on reads/writes |
| `auth:v1:{uid}:session-access:<sid>` | Sorted set: active `jti` → access deadline, for eager logout cleanup | Latest access deadline; prune expired members |
| Short-lived refresh replay/retry keys | Consumed nonce hash and tightly bounded retry result bound to the same session/request | Explicit retry/replay retention bound |

The access key makes **every active JWT issuance** independently represented, if that literal requirement is desired. Without individual-token revocation, a session record plus version is sufficient and cheaper; keep the per-`jti` keys only if their control/visibility is useful. A session key lasts across JWT rotations; an access key lasts only minutes. Do not set every access key to 30 days.

Never store the bearer JWT or refresh secret as the Redis key/value. Use a random identifier and SHA-256 fingerprint for a JWT; hash a high-entropy opaque refresh secret (optionally keyed with a server pepper). Refresh envelopes may contain identifiers plus the random secret; identifier possession alone grants nothing. No credentials in logs, analytics or device listings.

JWT claims: pinned algorithm/key ID, issuer, audience, `sub=uid`, `sid`, random `jti`, generation, authorization version, `iat`/`nbf`/`exp`. Start with roughly 5–15 minutes of access lifetime, pending policy. Verify signature, allowed algorithm/key, issuer/audience, timestamps, size and claim format **before** Redis. Do not dynamically fetch attacker-selected keys. Then one bounded Redis script validates user, session and access records, matches claims/fingerprint, checks deadlines/current permissions, and optionally records activity. Atomic scripts prevent check/update races, but require a separate audit of error handling: script errors are not transaction rollback. [Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/).

## Lifecycle and inactivity

After initial Clerk verification and account eligibility checks, create user/session/access/index state atomically, then return credentials only after successful writes. Failure creates no usable login. Renew access using the independent refresh credential after Clerk expires; continued Clerk session validity cannot be a renewal prerequisite.

Use **30 days since meaningful authenticated activity**, bounded by a configurable independent absolute lifetime, for example 90 days pending product choice. A fixed 30-day deadline from login is a different policy: returning after 21 idle days can fail when the login was already older than nine days. A rolling return works only while the absolute deadline also remains ahead. Extend idle deadline and Redis expiry atomically only for existing, authorized state; never upsert/recreate a missing session or user gate on validation/refresh. Updating Redis TTL cannot extend a JWT's fixed `exp`; refresh issues a new JWT/access key, capped at effective session expiry. Activity writes may be throttled with a documented boundary tolerance; foreground refresh and explicit activity must update the deadline accurately.

Background polling, hidden tabs and live-tab heartbeats must not silently keep an abandoned login alive. Stop authenticated polling when signed out; suspend unnecessary hidden/inactive polling. Use app foreground/user activity signals, with native reopen/refresh support. SSE/WebSocket connections must reauthenticate by access expiry and enforce remote revocation; opening a socket once is insufficient.

Refresh rotation atomically compares secret hash/counter, consumes the predecessor, installs a successor, and issues a new access record. Serialize refresh per client session across web tabs. Define a short idempotent retry window for a lost response; bind retries to a request nonce and the same credential/session, and protect any temporarily stored successor credential. Outside that window, proven reuse of a previously consumed secret revokes the session. An arbitrary wrong secret must not revoke another person's session. Keep consumed-secret evidence only as long as the explicit reuse-detection policy needs; no permanent token history in Redis. Rotation need not invalidate all earlier access JWTs immediately; session revoke/version change does.

Current-device logout atomically deletes the session, index member, refresh authority and indexed access keys. Bound session/token counts to keep scripts short; remaining cleanup can be batched after immediate invalidation. Revoke-all atomically increments the user generation and blocks all old sessions/refreshes; cleanup can follow. A missing user gate rejects credentials; old claims cannot recreate it. Account deletion/disable and security events must use this same gate across web/API/live services. Current authorization must come from Redis, not potentially stale JWT role claims. A mutation already authorized before revocation may finish; sensitive operations can recheck just before committing.

## Expiry, stale keys and operations

Create/update records **with their expiry in the same operation/script**. Redis passively rejects expired keys on access and actively reclaims expired keys periodically; physical removal is not guaranteed at the exact deadline. Also check stored deadlines. Native expiry is the correctness mechanism; a nightly scan is optional repair/metrics, not the validator. [Redis EXPIRE](https://redis.io/docs/latest/commands/expire/).

Sorted-set members do not inherit independent TTLs from session keys. Prune by score, check session existence when listing, remove members on logout, and expire each index at its latest member deadline. Session renewal extends the user gate/index retention atomically; a shorter-lived login must never decrease their existing maximum deadline. Refresh retry/replay records and user gates also need deliberate retention. Durable audit history belongs outside the online credential store.

Isolate auth from live-tab snapshots in a **separate instance**, with `noeviction`, TLS/network restrictions, bounded command timeouts and narrow ACLs. Logical database numbers do not isolate shared memory policy or failures. Capacity alarms must precede exhaustion; `noeviction` preserves keys but may reject writes, so login/refresh failure returns `503`, never unrecorded credentials. [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/).

Persistence/replication need an explicit acceptable data-loss and outage policy. Lost login writes cause false rejection; lost logout/generation updates can resurrect revoked access. AOF settings and replication reduce risk, but ordinary asynchronous Redis failover can lose acknowledged writes; `WAIT` does not establish strong consistency. Read from the authoritative primary, avoid stale local allow-caches, and require failover/restore fencing. If freshness cannot be proven, block validation and rotate an externally maintained deployment generation before reopening, forcing old sessions to reauthenticate. Proving timely detection/fencing is a release prerequisite; Redis alone cannot promise revocation survives every failure. [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/).

SQL/Redis have no shared transaction. Route all credential changes through one lifecycle service with idempotency and durable operation records; define partial-failure recovery before building. Never rebuild live allowlist entries from an old SQL session row or restored Redis snapshot. Controlled rebuild requires a current authoritative journal/generation and blocked traffic; otherwise require fresh login. If strict durable revocation without global logout is required, choose infrastructure with verified consistency guarantees or accept durable-store checks on sensitive paths.

Upstash is not present in the targeted source scan. If considered, verify actual selected-product semantics: its current consistency page describes eventual consistency and deprecated strong mode. Cross-region/connection read-your-writes is insufficient proof of immediate revocation everywhere. [Upstash consistency](https://upstash.com/docs/redis/features/consistency).

Before implementation approval: select individual-JWT tracking, absolute lifetime, meaningful-activity definition, security-event policy, infrastructure/fencing and migration scope. Acceptance must prove zero SQL calls for absent/malformed/forged/expired credentials and valid Redis misses; multi-tab concurrent/lost-response refresh; 21-day idle return and exact expiry limits; copied-token logout, revoke-all, deletion/permissions; index/key retention; signing-key changes; outages/OOM; stale replica/failover/restored-snapshot revocation; and API/live agreement.
