# Supabase authentication migration — approval plan

4 October 2026. Proposal only. Replace Clerk authentication; preserve existing Turso bookmark databases, tenant identities, app identifiers and Google/Apple registrations.

1. **Prepare identity and providers.** Snapshot account mappings, configure isolated test accounts, Google/Apple callbacks, email verification/recovery and production SMTP. Map verified provider subjects and Supabase UUIDs to existing canonical account IDs; never auto-link by email. Verify Apple subject continuity. Password accounts use compatible hash import only when available, otherwise password reset. Existing users should expect one new sign-in.

2. **Replace backend authentication.** Update Next.js page/API guards, account/profile/deletion flows, provisioning and webhooks, macOS login exchange, and OCI Live authentication. Verify Supabase JWTs through asymmetric signing keys/JWKS. Preserve tenant data paths, authorization scopes, analytics identity and account isolation.

3. **Use Supabase-managed sessions and online validation.** Supabase owns native session records, rotating refresh credentials and sign-out. Free sessions have no fixed maximum by default, meeting the two–three-week inactive-return goal without an auth Redis registry or enrollment hook. Remove proposed 30/90-day limits; exact managed inactivity/maximum limits require Pro. Every protected human-session request must verify issuer/audience/signature/expiry and a native `session_id`, then call `supabase.auth.getUser(accessJWT)`. Current Auth source rejects a missing native session, including an unexpired JWT after that session is removed. `getClaims()` alone is insufficient; no positive session cache across requests. Reject invalid JWTs early, rate-limit requests, and return a temporary service error during Auth outages while preserving client credentials. Short JWTs (proposed 15 minutes) and cached signing keys remain useful, but do not replace online checks. [Sessions](https://supabase.com/docs/guides/auth/sessions), [getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [Auth session lookup](https://github.com/supabase/auth/blob/master/internal/api/auth.go#L109).

   **Device controls are a required parity gate.** Supabase has native session/device metadata and documented current/all/other-session logout. The inspected public SDK/API has no session-list or arbitrary session-ID revoke method. A narrow own-user interface over native `auth.sessions` is technically feasible; native logout deletes that row and its refresh tokens cascade. Direct selected-row deletion is not an established public device-management API contract, so do not silently adopt it under the user's no-workarounds requirement. Establish supported selected-device management and verify its lifecycle before Clerk cutover. No parallel session registry or retention of another device's bearer is permitted. [Sign-out scopes](https://supabase.com/docs/guides/auth/signout), [admin SDK](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueAdminApi.ts#L128).

4. **Convert every active client.** Web/PWA; Swift macOS; Expo iPhone/iPad/Android, including share flows; Chrome MV3, Firefox MV2 and Safari MV3 macOS companion/extension. Replace Clerk UI/state with Supabase and equivalent account controls. Preserve native Apple login, Google browser login, PKCE/callback protections, SecureStore/Keychain and App Groups. Extension credentials remain restricted. Public docs remain public; the separate Zig desktop experiment is outside active release scope.

5. **Preserve Bookmark AI MCP.** Current code issues application-owned `bkmcp_` JWTs with a token-ID revocation ledger; no Clerk JWT-template dependency was found. Keep endpoint, tools, credentials and their separate expiries. Switch token creation/revocation/settings login to Supabase. Existing integration credentials retain their database revocation ledger, separate from human sessions; no new Redis auth layer is needed. Use [Supabase OAuth 2.1](https://supabase.com/docs/guides/auth/oauth-server/mcp-authentication) if an existing host requires it. Replacing all legacy MCP credentials with provider-issued OAuth requires an explicit compatibility/cutover decision.

6. **Stage compatibility and rollback.** Accept Clerk and Supabase during a finite release window; legacy extension tokens retain their existing limited scope and receive an explicit sunset. They lack individual device IDs, so per-device revocation cannot be promised retroactively. Update clients in cohorts. Retire Clerk and its deletion webhook only after migration gates pass; historical Clerk deletion events must not destroy migrated accounts.

7. **Verify and release.** Test signup, both social logins, recovery, logout, device-session controls, deletion, existing-library continuity and tenant isolation on every client. Simulate 21-day inactivity, access-token expiry, refresh races, offline/provider-outage recovery and revoked-refresh-token reuse. With two test sessions on the selected hosted project, retain A's access JWT, revoke A from B, and prove the next protected request rejects A before JWT expiry while B remains valid and A cannot refresh. Verify wrong-user revocation denial, credential redaction, rate limits, request races, and bounded Live stream revalidation/disconnection; in-flight work is not retroactively canceled. Check MCP hosts and PostHog/Langfuse identity continuity. Rebuild affected packages, update privacy/review notes and repeat three Apple demo recordings. Resolve existing Mac trust/build, Firefox QA-window and physical-device preflight blockers.

**Execution:** GPT-6.1 Sol high/xhigh agents in coordinated backend, web, native and extension waves, followed by separate QA. Estimate **2–4 working weeks**, plus store-review waiting; unusual identity/password or MCP-host requirements may extend this.

**Owner inputs only when needed:** securely supplied provider/backend credentials, SMTP settings, dashboard configuration authorization and device/reviewer sign-in handoffs.
