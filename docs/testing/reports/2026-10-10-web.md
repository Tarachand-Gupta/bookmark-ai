## Provider behavior discovered during QA

The first combined run passed19/20 assertions, then stopped because a session created before MFA confirmation returned401 rather than the harness's expected403. Successful MFA verification invalidates lower-assurance sessions; [Supabase's upstream verification transaction](https://github.com/supabase/auth/blob/master/internal/api/mfa.go#L726-L735) explains the observed behavior. The new factor and all three new sessions were cleaned up. That first run retained preexisting-session preservation through revocation, but did not persist its pre-MFA baseline IDs/count; no retroactive full preservation claim is made for that first factor operation.

The final MFA run persisted and enforced **zero preexisting sessions before enrollment**, then created its AAL1 test session after confirmation. Its checks passed. A second harness expectation required401 for a late revoked challenge; the provider correctly returned403. The final run captured the JSON `session_not_found` error and accepted this explicit authorization denial. Neither observation establishes a product defect. Existing owner/shared-client accounts and sessions were never used.

Current source gates: `apps/web/lib/server/supabase-auth.ts` verifies the provider session and enforces verified-factor AAL2; `session-management.ts` delegates exact-session operations to the owned-account function; `supabase/schemas/bmai_qa.sql` binds session operations to caller/current-session ownership. Source inspection is separate from the real results above. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [refreshSession](https://supabase.com/docs/reference/javascript/auth-refreshsession), [MFA guide](https://supabase.com/docs/guides/auth/auth-mfa) and [verify](https://supabase.com/docs/reference/javascript/auth-mfa-verify) were checked; the relevant changelog and monitoring documentation were fetched.
