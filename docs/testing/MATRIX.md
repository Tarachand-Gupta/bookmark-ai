# Repeatable journey matrix

Use [runbook modes/accounts](RUNBOOK.md) and [the report template](RUN-REPORT-TEMPLATE.md). Every row is a case specification, **not a claim it passed**. Execute separately per applicable client/artifact/mode. P0 is the first acceptance gate; P1 completes the main product; P2 exercises edge/security/destructive cases. A blocked dependency does not block unrelated rows.

Ordering is risk-based, not a rule that P2 is optional or last. For an auth migration/release, actual email/recovery/MFA/refresh/revoke (`AUTH-06`–`AUTH-10`), cross-user/token containment (`ISO-01`/`ISO-02`) and MCP scope/revocation are release gates and move ahead of cosmetic P1 cases. If A has no Supabase password, establish it through verified recovery (`AUTH-07`) before password login (`AUTH-01`), or use its established provider for the independent journey. Destructive account deletion still comes last and requires its own scope.

## Exit criteria and updating coverage

A client is usable for a basic production trial only after its exact installed artifact passes the applicable P0 auth/data/restart cases. Full E2E acceptance includes the applicable P1/P2/MCP rows; report every unsupported or blocked case. Store release additionally needs distribution/signing/store-review gates outside this matrix.

Each run adds client/mode/status/time/evidence to the report rather than ticking this document globally. Revisit the dated gaps in [README](README.md), preserve earlier evidence, and append fixes/new artifact identity. Add new stable case IDs when features appear; map source tests to those journeys without treating assertions as all-device evidence. Never remove a failing case just because one harness cannot reach it.
